# CSBox v0.3 Lab Session Correctness Design

## User problem

Lab currently conflates child-process exit with CSBox recording failure, leaves
sessions in `running`, persists Capture before the ordered event pipeline has a
transaction result, and renders Review without enough lifecycle or corruption
state to explain an empty or failed recording. The Batch 1 path must make
`start -> output -> Capture -> exit -> persist -> Review` reliable on the
existing Unix and Windows backend abstractions.

- pyte: parser/stream ordering and screen-owned terminal state.

## Not copying

This design does not add raw keyboard recording, Windows Terminal host-key
diagnostics, ConPTY resize/reflow work, cursor fixes, or a new Lab TUI surface.
It uses the references as behavioral guidance only.

## Invariants

1. Metadata is created in `starting` before spawn. `running` is written only
   after the recorder and terminal process boundary are established.
2. Normal EOF and any child exit code produce `completed`; non-zero child exit
   codes remain metadata and do not become CSBox `failed`.
3. PTY/read/recorder/critical-persistence failures produce `failed`, while
   user interruption produces `interrupted`. Stale `running` records are
   recovered using owner/process evidence and an explicit reason.
4. The recorder sees only events emitted after the session boundary. Every
   terminal event is applied to the emulator and then dispatched in one
   sequence; status messages never enter child input, output, or the cast.
5. A received Capture key is consumed, creates one ordered Capture event, and
   commits snapshot, metadata, marker, and count as one logical transaction.
   Capture-local failure returns a result and leaves a healthy session alive.
6. Review exposes lifecycle status, current time, duration, event count,
   Capture count, playback state, warnings, and controlled empty/failed/
   interrupted/corrupt states. Space only toggles play/pause; Esc/Q returns.

## Proposed architecture

Keep `TerminalProxy` as the single ordered event owner. Add explicit lifecycle
and result values at the service/repository boundary, and make Capture
handling return a structured success/failure result rather than raising into
the process loop. Extend replay parsing with immutable diagnostics that Review
can render without reconstructing status from a black screen. Keep UI status
outside the terminal event stream so a later TUI can subscribe to it.

## Error handling

Recorder and cast parsing failures are infrastructure failures and are retained
as lifecycle warnings/reasons. A single Capture sidecar or marker failure is
reported through the status/result channel and does not close the child. A
truncated or invalid cast is readable only through a controlled Review state;
valid events before the damaged tail remain replayable.
